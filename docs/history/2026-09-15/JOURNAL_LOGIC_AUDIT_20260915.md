# 按钮闭环日志与状态结构审计（2026-09-15）

## 结论

旧日志不能单独作为“按压完成”或“已回原点”的充分证据。执行逻辑本身大多具有硬件检查，但若检查失败，结果没有总能写入日志；部分上层事件又把“函数正常返回”错误地表述成物理成功。本次将日志改成带证据的状态事务，并把流程失败传给进程退出码。

## 历史证据

扫描 `button_light_closed_loop_runs/*/closed_loop_report.yaml` 的 82 份报告得到：

- 61 份报告声明 `returned_to_origin: true`，但都没有保存末次编码器误差与 `hardware_ok` 证据。
- 51 份报告包含旧事件 `press_completed`。该事件只能证明按压函数返回，不能区分力反馈确认、达到位移上限后回撤，或反馈不完整。
- `20260911_130534` 的 `observation_to_prepress` 有开始事件，没有对应完成、反馈未确认或失败事件。
- `20260914_150652` 已保存 22 条执行记录，但顶层状态仍为 `initializing`，无法区分运行中、异常退出或残留文件。
- `20260914_093400` 把恢复阶段的“视觉安全停止仍有效”写入 `failure_robot_state_error`，错误地暗示机器人状态读取失败。
- 日志目录在旧版指向阶段之后才创建；指向阶段失败时可能完全没有父流程报告。

这些旧报告保持原样，审计工具会明确标记其证据缺口：

```bash
python3 tools/audit_closed_loop_journals.py button_light_closed_loop_runs
```

## 修正后的数据流

1. 父流程在任何指向动作前创建 `schema_version: 2` 报告。
2. 每条日志具有递增 `sequence`、单调时钟、Unix 时间、明确 `phase`。
3. 每段轨迹在发送前生成 `task_id`；开始、完成、失败、安全清理失败和终点校验失败使用同一个 ID。
4. 轨迹桥返回后必须读取机器人状态。只有 `hardware_ok == 1` 且编码器误差在阈值内才写 `motion_segment_completed`。
5. 力控按压结果从执行器逐层返回状态机。状态机写 `press_attempt_finished`，并保存桥状态、原因、力反馈是否确认及回撤终点误差。
6. 灯态仍是按压是否生效的业务证据。`press_verified_on` 只在两张独立新帧一致为 ON 后产生。
7. 回等待位与回原点事件携带执行器或编码器验证结果；顶层 `returned_to_origin` 只由最终实测生成。
8. `status` 保留兼容字段，同时新增 `lifecycle_status`、`flow_status` 和 `process_exit_code`，避免把进程生命周期与业务结果混在一起。

## 修正的误导字段和故障路径

- `press_completed` 改为 `press_attempt_finished`，避免把安全回撤误报为接触或点亮成功。
- 5 cm 字段改为 `requested_panel_distance_m`。它是计划请求值，不再伪装成传感器实测距离。
- 终点编码器读取失败、误差超限或 `hardware_ok != 1` 都会写带 `phase` 的 `motion_segment_failed`。
- 安全清理失败同时写 `motion_segment_cleanup_failed`；若此前没有主错误，还会闭合为 `motion_segment_failed`。
- 原点附近但 `hardware_ok != 1` 不再被判为已回原点。
- 恢复跳过会记录具体阻断原因；恢复动作失败写入 `failure_recovery_error`，不再冒充状态读取错误。
- 初始观察不确定、灯未亮且重试耗尽等业务失败返回退出码 2；未处理异常返回 1；成功返回 0。
- 清理阶段异常会保留原始异常；若主流程本来成功，清理失败会把报告改为失败并使进程非零退出。

## 保留的行为与边界

- 按钮持续为 ON 时无限等待是当前明确的业务要求，不作为卡死处理；每 10 秒写等待心跳。
- 操作系统 `SIGKILL`、断电或磁盘损坏无法由进程补写终态。新版报告会保留最后一个有序阶段，审计工具将非终态标为异常。
- 历史报告没有缺失的编码器样本，无法事后补证，因此不能把旧 `returned_to_origin: true` 自动升级为已验证事实。
